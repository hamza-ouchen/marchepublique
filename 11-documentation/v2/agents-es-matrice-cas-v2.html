0. Qui intervient quand — FastAPI ou agent ? (règle nouvelle en v2)

🔑 La règle d'or : FastAPI seul fait tout ce qui a une règle fixe (valider, stocker, générer un lien, envoyer un gabarit, lire un résultat). Un agent n'est appelé que s'il faut comprendre une phrase libre, expliquer avec citation, ou formuler un texte.

0 bis. Le parcours d'inscription officiel (aligné sur le projet Soukna original)

Sources : KB soukna-kb-01-plateforme-fr.md (« invitation personnalisée, lien unique valable 7 jours, par email et WhatsApp ») · landing form.html (« Demander un accès anticipé ») · runbook (canaux ignorés si panne, dashboard toujours alimenté).

CAS 0Du premier contact à l'activation — le parcours officiel

1
FastAPI le visiteur remplit le formulaire landing = file d'attente (« Demander un accès anticipé ») — email professionnel obligatoire · WhatsApp facultatif · secteur obligatoire · consentement loi 09-08 + honeypot anti-spam → écrit dans prospects
2
HITL 1 l'équipe examine la demande dans la console d'admin (/admin/waitlist) et approuve
3
FastAPI génère une invitation personnalisée : lien unique, valable 7 jours, envoyé sur les deux canaux (email + WhatsApp) — gabarit fixe, sans agent
4
FastAPI le client ouvre le lien → page onboarding → confirme son profil + choisit son mot de passe
5
FastAPI l'accès s'ouvre → essai gratuit de 14 jours démarre immédiatement (bandeau « jour X sur 14 ») → messages de bienvenue sur les 2 canaux
6
FastAPI canaux opt-in : WhatsApp + email activables depuis le profil ; le dashboard est toujours alimenté — si un canal échoue, les autres continuent (runbook)
7
CONCIERGE toute la suite : le client discute (WhatsApp / email / dashboard) — mêmes règles sur tous les canaux
🔑 Corrections v2 vs v1 : email obligatoire / WhatsApp facultatif (pas l'inverse) · lien valable 7 jours (pas 48 h) · lien envoyé sur les deux canaux · essai 14 jours dès la confirmation · le mot de passe se choisit à l'activation.
⚠️ Sécurité du lien (équipe bleue) : usage unique · expiration 7 jours · lié à l'entreprise (jamais un lien générique) · 3 tests permanents dans la suite rouge/bleue.

5. Les cas d'usage expliqués (v2)

CAS ALe run quotidien — de 6h00 à 8h00

6h00
RÉGISSEUR cron → POST /cron/run → run_logs = « ouvert »
6h05
INSPECTEUR collecte → écrire tenders → rapport au RÉGISSEUR
6h20
COMPAGNON 2 lectures batch → Match /100 (zéro LLM) → scores + digests
7h00
JUGE scores au-dessus du seuil → 4 contrôles → justification (LLM+RAG) → verdicts
7h30
COMPAGNON digests → envoi → statut « envoyé »
8h00
le client lit son digest · HITL 2 si À ÉTUDIER
18h00
RÉGISSEUR clôture le run → observabilité
🔑 Après chaque étape, le contrôle revient au RÉGISSEUR — les agents rendent leur rapport et s'arrêtent. Les données vivent dans la base ; le RÉGISSEUR ne les transporte jamais.

CAS BL'exécution manuelle par l'admin

Bouton dashboard → POST /run (token admin) → RÉGISSEUR. Le déclencheur change, pas le pilote : mêmes étapes, même tracé, mêmes HITL.

CAS C« Quelles offres cette semaine ? » — sur WhatsApp OU par email

CONCIERGE lit scores + verdicts (RLS) et répond sur le canal de la question — WhatsApp ou email, mêmes règles. Aucun appel à l'INSPECTEUR, aucune nouvelle collecte. Réponse avec fraicheur: "données du 17-11 08:00". Avant 8h00 : dernières données connues + « l'update arrive à 8h00 ».

CAS DClic « consulter » sur une offre — la fiche dossier

GET /dossiers/{ref} → base → affichage. Aucun agent : la consultation est un affichage, pas un recalcul (Match détaillé, verdict, justification, risques, sources).

CAS E« Comment gagner cette offre ? » — accompagnement & ligne rouge

CONCIERGE explique le dossier déjà calculé : points forts, points perdus, les 3 risques — avec citation.

🚫 Ligne rouge : écrire la soumission · promettre un gain · appeler quiconque → refus poli + HITL 3.

CAS FLe JUGE : objet vs tableau

objet = fiche d'une offre · tableau = lot du matin. risques_a_verifier (≥ 3) uniquement pour À ÉTUDIER.

CAS GLe portail est en panne — le mode dégradé

INSPECTEUR : 2 échecs → source: "secours" + état « dégradé » → digest quand même livré avant 8h00 avec bandeau. Jamais de silence client. Et si un canal est en panne (email/WhatsApp) : canal ignoré, les autres continuent, dashboard toujours alimenté (runbook).

CAS HQuestion hors périmètre — l'escalade HITL 3

« Rédigez-moi ma soumission complète » → CONCIERGE refuse poliment → RÉGISSEUR → HITL 3 un humain valide avant envoi.

6. Les 7 règles transversales (v2)

#Règle
1Tout passe par le RÉGISSEUR — aucun agent ne parle à un autre directement ; chacun rend son rapport et s'arrête.
2Les données passent par la base, pas par les agents — contrôle via RÉGISSEUR, données via la base, en batch.
3Collecte ≠ consultation — le portail n'est appelé que par l'INSPECTEUR (6h00 / run admin) ; les questions des clients lisent la base.
4On calcule une fois par jour, on consulte toute la journée — même entrée = même sortie (Match déterministe, versionné).
5Listé = autorisé, non listé = interdit — la matrice §3 fait partie du contrat de chaque agent.
6On prépare, on ne promet pas — toute action engageante est refusée et remontée à un humain (HITL).
7🆕 FastAPI fait les règles fixes ; les agents font le langage — valider / stocker / lier / envoyer un gabarit = FastAPI. Comprendre / expliquer / formuler = agent. L'inscription complète se fait sans aucun agent.
